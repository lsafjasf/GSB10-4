# spilldedup —— 内存受控的精确去重算子（纯标准库 Python 3）

内存装不下全部键时向磁盘溢写，且保证：**溢写/归并后的去重结果与内存充足时逐条一致**。

## 文件

| 文件 | 说明 |
|---|---|
| `spilldedup.py` | 算子库（`SpillDedup` / `dedup`），仅标准库 |
| `tests_selfcheck.py` | 18 个自测用例（unittest） |
| `bench_10m.py` | 1000 万条 / 64 MiB 预算基准 + 对拍 |
| `make_sample_data.py` | 重新生成 `data/` 下的固定对拍数据 |
| `data/sample_keys.txt` / `data/sample_expected.txt` | 固定对拍输入（1005 条）与期望输出（292 条） |
| `data/collision_demo.txt` | 哈希碰撞样例 |
| `bench_result.txt` / `bench_time.log` | 基准实测输出与 `/usr/bin/time` 外部测量 |

## 算法

1. `add(key)`：键被规范化为**带类型标签的字节串**（`encode_key`）进入内存缓冲，
   每条记录按保守公式计费；计费达到上限立即把缓冲**排序 + 相邻去重**，
   写成一个不可变溢写文件（run）。
2. `results()`：最后一块内存数据（同样排序去重）与全部 run 做 **K 路归并**
   （`heapq.merge`），归并流中相邻相等的键只保留一条，流式输出。

**判等只依赖规范化字节串的字节比较，全程不调用 `hash()`**（有测试断言源码中
不存在 `hash(`）。因此任何哈希碰撞在结构上都不可能造成误去重。

正确性论证：分趟是对输入多重集合的一次划分；每趟排序去重等价于在该趟内取
`set`；归并排序把全集合成一个有序序列后按相邻比较去重，结果 =
`sort(unique(全集))`，与一次性在内存中 `set` 去重的结果集合完全相同，
与内存上限取值无关（对拍测试覆盖 `limit=None / 1KB / 4KB / 8KB / 64KB`）。

## 内存上界与溢写触发点

**触发点**：每次 `add` 后检查 `已计费字节 >= memory_limit_bytes`，满足即溢写。
最后一块不足上限的数据在 `results()` 时于内存中排序去重，不落盘。

**每条记录计费**（保守高估）：`charge = sys.getsizeof(编码后bytes) + 64`，
其中 64B 覆盖 list 指针槽（8B）、list 预留/整体分配余量（≤8B）以及排序临时
数组、归并堆等按条摊销的余量（48B）。实测每条真实占用约 56B < 计费 108B，
即计费有约 2 倍余量。

**算子工作集上界**（不含解释器基线）：

```
W <= memory_limit_bytes          # 缓冲计费上限（触发即溢写）
   + L_max                       # 触发瞬间单条键的越过量（= 最大单键计费）
   + 1 MiB                       # 溢写批量写缓冲
   + 8 KiB * K                   # 归并时 K 个 run 的读缓冲
```

**进程级预算换算**：`memory_limit_for_budget(B) = B - 当前RSS - 2MiB安全余量`。
基准即用此法把「64 MiB 进程预算」换算为算子上限，实测峰值见下。

## 溢写文件的安全清理

- 每个实例使用独立目录 `<spill_dir>/p<PID>_t<启动时间>_<序号>/`，
  目录内 `owner` 文件记录属主 PID 与进程启动时间（clock ticks）。
- run 文件先写 `run-XXXXXX.bin.tmp`，`fsync` 后 `os.replace` **原子发布**；
  被 SIGKILL 时最多留下一个未发布的 `.tmp`，它从不参与读取。
- 正常路径：`results()` 迭代结束（含异常，`try/finally`）、`close()`、
  上下文管理器退出、解释器退出（`weakref.finalize`）都会删除实例目录。
- 崩溃路径：下一次构造任意 `SpillDedup` 时清扫 `<spill_dir>` 下
  **属主进程已死亡或 PID 已被复用**（对比 `/proc/<pid>/stat` 启动时间）
  的残留目录。残留文件在新实例的独立目录之外，即使不清扫也绝不参与
  下一次归并，不影响结果（有 SIGKILL 实测用例验证）。

## 哈希碰撞验证

- 样例（`data/collision_demo.txt`）：64 位 CPython 上
  `hash(0) == hash(2**61-1) == 0`（`int` 哈希取模 `2^61-1`）。
  测试把这对碰撞键各重复 5000 次喂给算子，两者都保留，结果与参考一致。
- 结构性保证：算子源码无 `hash(` 调用（测试断言）。
- 同一负载在 `PYTHONHASHSEED=0/1/42` 三个子进程中输出逐字节一致。

## 基准实测（1000 万条，64 MiB 预算）

环境：Python 3.12.3，WSL2 x86_64（16 核）。数据流：确定性生成
`b"k%09d"`（10 字节键），取值空间 300 万，种子 20261005。

```
输入键数        : 10000000
输出唯一键数    : 2892792
溢写 run 数     : 22
溢写文件总大小  : 163.47 MiB (171414620 字节)   # 归并后即全部删除
灌入耗时        : 12.28 s
归并输出耗时    : 4.08 s
总耗时          : 16.36 s
进程峰值内存    : 45.16 MiB (预算 64 MiB) -> 达标
```

- 进程峰值内存另有 `/usr/bin/time -v` 外部测量佐证：
  `Maximum resident set size: 46244 KB`（= 45.16 MiB）。
- 对拍：算子输出的滚动摘要（BLAKE2b，长度前缀防拼接歧义）与
  「同一数据流装入内存 `set` 后排序」的参考摘要**逐位一致**：
  `c8e0d6c4…29ab1aad`（2,892,792 条）。

## 语义说明

- 支持键类型：`bytes / str / int / bool`；`bool` 与 `int` 视为不同键
  （`True` 与 `1` 都会保留），跨类型绝不相等。
- 输出按**规范化字节序**升序：`int` 按十进制字符串字典序
  （`1, 10, 2, …`），`str` 按 UTF-8 字节序。去重结果集合与顺序无关，
  对拍均按同一规范比较。
- 内存上界约束的是算子工作集；调用方若把输出收集成列表，那部分内存
  属于调用方（基准采用流式消费，故进程峰值达标）。
