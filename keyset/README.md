## 翻页方式：键集分页（游标 = 值，不是位置）

**OFFSET 为什么慢**：`LIMIT n OFFSET m` 每页都要从索引头部扫描并丢弃 m 行，
单页耗时 O(m)，页号越大越慢 —— 这就是"每次还在从头数过去"。

**键集分页**：每页返回最后一行的排序键 `(score, id)` 作为游标，下一页直接定位：

```sql
SELECT id, score FROM t
WHERE (score, id) > (?, ?)      -- 上一页最后一行的 (score, id)
ORDER BY score, id
LIMIT ?                          -- page_size + 1（多取 1 行判断 has_next）
```

**为什么不会越翻越慢**：在 `(score, id)` 复合 B+ 树索引上，这是一次
**O(log N) 定位 + 顺序取 n 行**，与已经翻过多少页无关。第 1 页和第 10000 页走的是同一条路径。

两个实现要点（都踩过坑）：

1. **游标必须是复合键 `(排序列, 主键)`**。排序列有重复值时，单列游标会在
   重复键边界上重复/丢行；`(score, id)` 字典序比较保证严格推进。
2. **用行值比较 `(score, id) > (?, ?)`，不要展开成 `score>? OR (score=? AND id>?)`**。
   实测 SQLite 3.45 对 OR 形式放弃范围 SEARCH、退化为全索引 SCAN
   （单页 165ms vs 0.36ms，慢 400 倍）。行值比较需 SQLite ≥ 3.15（2016 年，标配）。

**数据变化时的一致性**（游标是"值"而非"位置"，天然免疫位移）：

| 变化 | 键集分页行为 |
|---|---|
| 游标之前插入/删除行 | 不影响后续页，**不重复、不跳过**（OFFSET 会整体位移导致重复/丢失） |
| 游标之后插入行 | 后续页中**恰好出现一次** |
| 删除尚未翻到的行 | 该行不再出现，其余行不受影响 |
| UPDATE 把排序键从游标前改到游标后 | 该行会再次出现 —— 所有键集分页的固有语义，如需严格一次性请配合快照/版本列 |

## 边界测试结果（翻页期间数据变化）

`selftest.py` 第 [3] 组：翻到第 1 页（id 1..100）后注入变化，再继续翻到末页：

| 注入的变化 | 键集分页实测 | OFFSET 对照 |
|---|---|---|
| 游标前插入 10 行（score 50..59） | 未重复输出 ✅ | **重复 9 行** ❌ |
| 游标后插入 5 行（score 150..154） | 恰好出现一次 ✅ | — |
| 删除未翻到的行 id=250 | 不再出现 ✅ | 位移导致后续错位 |
| 删除已输出的行 id=30 | 无影响 ✅ | — |
| 最终序列 vs 期望值 | 1004 行逐一相等、零重复 ✅ | 集合不等 ❌ |

期望值定义：`已输出的第 1 页` ∪ `变化后库中所有 (score,id) > 游标(100,100) 的行`，
实测序列与其完全相等（含顺序）。

第 [3b] 组（UPDATE 语义，已文档化）：排序键从游标前改到游标后的行会再次出现
（`emitted.count(5) == 2`），改到游标前的行不再出现，其余行无重复无遗漏。

第 [4] 组退化情形：空表（首页即空、无下一页）、单行、page_size > 总行数，全部通过。

## 用法

```python
import sqlite3
from keyset_page import KeysetPaginator

conn = sqlite3.connect("app.db")
# 前提：CREATE INDEX idx ON t(score, id);
pag = KeysetPaginator(conn, table="t", order_col="score", pk="id", page_size=100)

page = pag.first_page()          # 首页
cursor = page.cursor             # 不透明字符串，可放 URL/JSON 传给前端
page2 = pag.next_page(cursor, page_no=2)   # 下一页；page.has_next 判断是否还有

for row in pag.iter_rows():      # 或直接全量流式遍历
    ...
```
