# genpool — 分代 + 预热对象池（Python 3 标准库）

## 运行

```bash
python3 test_genpool.py    # 8 个场景全量自测，输出存档见 run_output.txt
```

文件：`genpool.py`（库）、`test_genpool.py`（自测+基准）、`run_output.txt`（实测数据）。

## 预热数量的确定依据（不拍脑袋）

先 `calibrate()` 实测工厂冷启动均耗 `t_create`（中位数，本机 0.574 ms），再按：

```
warmup = min( max_size,
              ceil(warmup_budget / t_create),          # 预热总耗时有界
              ceil(expected_qps * t_create * headroom) )  # 覆盖创建窗口内的到达量
```

- `qps * t_create`：创建一个对象期间会到达的请求数——预热至少要覆盖它们，否则全付冷启动价；
- `headroom`（默认 2.0）：突发余量；
- `warmup_budget`（默认 50 ms）：预热本身不许拖慢启动；
- `max_size`：永不超容量。

实测（场景 1）：`t_create=0.574ms, qps=2000, headroom=2 → warmup=3`，预热实耗 1.7ms（预算内）。
场景 6 对照：200 并发突发下，预热 1 个 → 199 次 miss、117.9ms；预热 201 个 → 0 miss、0.1ms；预热 256 个 → 同样 0 miss 但预热多花 33ms 且多占 56×4KB 内存等回收。

## 分代规则与回收时机

| 代 | 晋升条件 | 空闲回收 TTL（默认） |
|----|----------|---------------------|
| GEN0 年轻代 | 新建 | 2s |
| GEN1 中年代 | 复用 ≥ promote_at(3) 次 | 30s |
| GEN2 年老代 | 复用 ≥ tenure_at(16) 次 | 300s |

回收时机：每次 `release` 惰性触发（每 256 次至多一次，短锁保护，均摊 O(1)），或后台线程周期 `sweep()`；规模降到 `min_idle`（预热水位）即停，水位不塌。

各代数量随时间变化（场景 2，TTL=0.4/1.2/3.0s）：

```
 t(s)  size  idle   G0   G1   G2  reclaimed
 0.0    12    12    0    6    6      0   热用后
 1.3     6     6    0    0    6      6   GEN1 到点回收
 3.3     1     1    0    0    1     11   GEN2 到点回收, 保底 min_idle=1
```

长期空闲（场景 7，突发 80 后闲置）：t=0.35s 回收 60 个 GEN0，t=1.2s 回收 19 个 GEN2，最终停在 min_idle。

## 干净复用（残留检测）

归还时 `reset(obj)`/`obj.reset()`；失败或 `verify_clean` 不通过 → 丢弃缩池，绝不放回。
实测（场景 3）：弄脏-归还 20,000 次 + 再借出 5,000 次逐一检查，残留 0 次。

## 容量上界与超限

`max_size` 硬上界（空闲+借出）。超限策略三选一：`discard`（临时对象即还即弃，默认）、`raise`、`block`（超时抛 `PoolExhausted`）。实测（场景 4）三种模式下 size 均 ≤ 8，永不越界。

## 100 万次借还（场景 5，16 线程并发）

| 指标 | 数值 |
|------|------|
| 总耗时 | 4.81 s（207,934 ops/s，4.81 μs/次） |
| 命中率 | 100.0000%（hits=1,000,000，misses=0） |
| tracemalloc 峰值 | 0.12 MiB |
| 进程 RSS 峰值 | 13.6 MB（基准 13.4 MB） |
| 池规模 | 16（上界 256） |

性能说明：借/还热路径无锁（`deque.popleft/append` 在 GIL 下原子），仅新建/容量判定/回收走锁。
对照实验：全局锁版本 16 线程仅 1.7 万 ops/s，无锁快路径 2400 万 ops/s。

## 异常情形覆盖

- **预热不足**（场景 6）：突发全部付冷启动，200 次借还 117.9ms vs 预热合理 0.1ms；
- **预热过量**（场景 6/7）：预热多花 33ms，多余对象由分代 TTL 回收，不长期占内存；
- **长期空闲**（场景 7）：按代际 TTL 逐级回收，保底 min_idle 随时能再扛突发；
- **借出不还**（场景 8）：泄漏 10 个后池靠 discard 兜底继续服务 1000 次，size 仍 ≤ 16 不无界增长；`snapshot()['borrowed']` 长期 >0 可作泄漏告警指标。
