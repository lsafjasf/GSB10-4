# 复杂度说明与实测数据

## 数据结构

- 最小堆 `_heap`：元素为 `[due, seq, id, payload]`，堆序即投递序。
- `_by_seq`：seq → 条目（挂账权威表）。
- `_id_to_seq`：id → seq（取消用）。
- `_delivered_ids`：当前 WAL 代内已投递 id 集合（取消判定用）。

## 复杂度

| 操作 | 复杂度 | 说明 |
|---|---|---|
| `schedule` | O(log n) | 一次 heappush + 常数级 WAL 追加 |
| `cancel`（未到期） | O(1) 期望 | 只删两个 dict；堆条目惰性作废 |
| `cancel`（已投递/不存在） | O(1) | 集合/字典查询 |
| `pump` | O((k + s) log n) | k = 本次到期条数，s = 惰性作废的废堆顶数；**只看堆顶，不扫描未到期堆积** |
| `snapshot` | O(n log n) | 排序 + 顺序写盘 |
| 恢复 | O(n log n) | n 条挂账记录逐条 heappush |

关键点：`pump` 的代价只与「本次实际到期的消息数」成正比，与未到期
堆积量无关——堆顶比较一次即可知道「没有到期消息」。

## 实测（Linux x86_64, Python 3.12.3, N = 1,000,000）

原始输出存档：`docs/data/benchmark_results.txt`（`python3 bench/benchmark.py`）。

| 项目 | 实测 |
|---|---|
| 插入 100 万条（不写盘 fsync，`durable=False`） | 17.2 s，约 58,000 ops/s（17.2 µs/op） |
| 插入（每条 fsync，`durable=True`，2 万条采样） | 约 740–750 ops/s（受磁盘 fsync 延迟限制） |
| 内存峰值（100 万条挂账） | tracemalloc 263.5 MiB；进程 RSS 峰值约 795 MiB（≈833 B/条） |
| 扫描：0 条到期 / 100 万堆积 | 7.5–8.4 µs（一次堆顶比较） |
| 扫描：1 万条到期 / 100 万堆积 | 0.131–0.135 s（13.1–13.6 µs/条） |
| 扫描：1 万条到期 / 1 万堆积（对照） | 0.128 s（12.8 µs/条） |
| 快照 100 万条挂账 | 15.2 s，文件 68.5 MiB |
| 恢复 100 万条挂账 | 7.5–7.8 s |

「1 万到期 / 100 万堆积」与「1 万到期 / 1 万堆积」的每条投递成本
（13.1 vs 12.8 µs）基本一致，验证了扫描代价不随未到期堆积增长。

## 说明

- `durable=False` 仅用于基准/测试：跳过每条记录的 fsync，崩溃可能丢
  最近记录；生产用默认 `durable=True`。
- 内存约 833 B/条（id 为小整数、payload 为 None 的实测值）；每条消息
  含堆条目 list、两个 dict 项及整数对象。若需更低内存，可换
  `array`/sqlite 等方案，但会牺牲纯标准库内存结构的简单性。
