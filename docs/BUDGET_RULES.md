# 请求链路超时预算切分规则

实现：`src/budget_chain.py`（Python 3，仅标准库）。时间单位：毫秒。
时钟与睡眠均由调用方注入（测试用 `FakeClock`，生产默认 `time.monotonic` / `time.sleep`）。

## 1. 模型

- 请求进入系统时创建一份预算：`deadline = 进入时刻 + total_ms`，**绝对截止时间**，
  全链路共享，不随段推进而重置。
- 链路 = 若干 `Stage` 顺序执行；每段可配置权重、最大尝试次数、单次硬上限、
  最小可用授权、退避参数。
- 段函数是**合作式**的：库把本次尝试的授权时长 `grant_ms` 传给它，
  它必须在此时间内返回或抛 `TimeoutError`。

## 2. 已用时间的度量口径

- 口径：**包络单调时钟**。`observed = max(raw_clock(), 历史最大观察值)`。
  时钟回拨不会让预算变多；回拨窗口内流逝的时间不计（这是单调时钟的标准取舍，
  保守方向是"少算已用"而非"多给预算"）。时钟前跳（STW、调度停顿）如实计入。
- 计入预算的时间：排队等待（`queue_wait_ms`，预算在进入系统、排队**之前**创建）、
  每次下游调用、重试间退避、以及库自身的调度开销（极小，见基准）。
- 每次判断都重新读时钟算 `remaining = deadline - now`，没有任何缓存的"剩余额度"。

## 3. 切分规则

第 i 段开始时，设剩余预算 `R`、剩余权重和 `W = w_i + ... + w_n`：

```
stage_slice_i = R * w_i / W          # 动态切分：前段省下的自动留给后段
attempt_grant = min(remaining_now, stage_slice / 剩余尝试次数, max_attempt_ms)
```

- 等权 n 段时首段名义份额即 `R/n`；实际用不完的份额随 `R` 自然滚入后段，无需回收。
- `max_attempt_ms`：单次尝试硬上限，防止某段一口吃掉全部剩余预算。
- `min_attempt_ms`：最小可用授权。剩余预算低于它时**不发起调用**，直接判耗尽
  （避免给下游一个注定完不成的超时，也避免"0.1ms 超时"式的无意义请求）。
- 授权 `<= 0` 时同样不发起调用。

## 4. 重试规则（重试消耗同一份预算）

- 同一段的第 k 次尝试只在**该段切片**内再切分：默认 `切片 / 剩余尝试次数`。
- 退避睡眠也消耗预算，且被钳制到剩余预算之内（`sleep_budget`）。
- 每次尝试前检查全局剩余；为 0 立即停止。
- 因此**重试次数不会放大总时长**：任意重试配置下，单请求总耗时 `<= total_ms`。
  10 万次基准中 `max(虚拟耗时) = 100.0ms = total_ms`，不变式成立。

消耗序列示例（预算 100ms，单段 3 次尝试，硬上限 35ms，退避 5→10ms）：

| 事件 | 起始 t(ms) | 消耗(ms) | 累计(ms) |
|---|---|---|---|
| 尝试 1（授权 min(100/3, 35)=33.33） | 0.00 | 33.33 | 33.33 |
| 退避 1 | 33.33 | 5.00 | 38.33 |
| 尝试 2（授权 min(66.67/2, 35)=30.83） | 38.33 | 30.83 | 69.17 |
| 退避 2 | 69.17 | 10.00 | 79.17 |
| 尝试 3（授权 min(33.33, 35)=20.83） | 79.17 | 20.83 | **100.00** |

对照朴素方案（每次尝试独立 35ms 超时、互不知晓）：`35+5+35+10+35 = 120ms`，
是预算的 1.2 倍；若每次给满 100ms 则为 315ms（3.15 倍）。完整序列见
`data/consumption_sequences.json`（由 `python3 demo_consumption.py` 生成）。

## 5. 提前停止（不指望各段各自兜底）

- 每段开始前检查全局剩余，`<= 0` 或低于 `min_attempt_ms` 即停止，后续段**不会被调度**。
- 段内每次尝试前同样检查。
- 段函数若不合作（无视授权、越过全局 deadline 才返回）：库在返回点检测越界，
  记 `overrun` 事件并显式返回 `exhausted`；越界之后不会再调度任何新工作，
  后续段的越界时间恒为 0。库是合作式模型，不假装能抢占正在运行的用户代码。

## 6. 结果语义（预算耗尽必须显式，绝不静默降级）

`ChainResult.status` 只有四种，全部显式：

| status | 含义 |
|---|---|
| `ok` | 全链路成功，`remaining_ms` 如实上报 |
| `exhausted` | 全局预算耗尽（排队吃光 / 尝试前无预算 / 低于最小授权 / 退避中耗尽 / 越过 deadline） |
| `stage_timeout` | 段内尝试次数用完且**全局预算仍有剩余**（如下游慢但预算够） |
| `stage_error` | 段抛出非 TimeoutError 异常，不重试，显式失败 |

每个结果都带 `reason`、`events`（逐事件消耗序列）、`attempts_by_stage`、
`elapsed_ms` / `remaining_ms`。不存在"超时了但返回成功/空结果"的路径。

## 7. 时钟回拨与前跳

- 回拨：包络口径，见第 2 节。已耗尽后回拨不会"复活"预算（有测试覆盖）。
- 前跳：如实计入，可能直接耗尽预算并触发提前停止（有测试覆盖）。
- 注意：包络只保护预算**观察到过**的高水位；段函数内部瞬间前跳又回拨、
  期间预算未读时钟，则无法被检测——这与所有单调时钟方案一致。

## 8. 边界用例（`tests/test_budget_chain.py`，14 个）

- 全部成功、剩余预算向后传递；权重比例切分
- 首段超时（链路中止，后续段不调度）；末段超时（预算有剩余 / 恰好压线耗尽两种）
- 重试耗尽（消耗序列断言）、重试后成功
- 排队计入预算、排队即耗尽
- 低于最小授权不发起调用（显式 exhausted，不静默）
- 非超时异常显式失败；不合作段越过 deadline 显式 exhausted
- 时钟回拨不放大预算、耗尽后回拨不复活、时钟前跳耗尽

## 9. 10 万次基准（`python3 benchmark.py` → `data/benchmark_100k.json`）

场景：每请求预算 100ms，排队 U(0,10)ms，三段等权、各 2 次尝试 + 退避；
70% 正常，每段各 10% 概率挂死。时间由 `FakeClock` 注入，墙钟只测调度逻辑本身。

实测（Python 3.12.3，x86_64 Linux，单次运行）：

| 指标 | 数值 |
|---|---|
| 单请求端到端调度耗时 | ≈ 21 µs（含场景构造） |
| 其中 `run_chain` 切分逻辑 | ≈ 16 µs |
| ok | 70.05% |
| exhausted（预算耗尽） | 10.00% |
| stage_timeout（段超时但预算有剩） | 19.94% |
| 虚拟耗时 max | 100.0ms（= 预算，无一超限） |

## 10. 运行命令

```bash
python3 -m unittest discover -s tests -v   # 自测（14 个用例）
python3 demo_consumption.py                # 消耗序列演示 → data/consumption_sequences.json
python3 benchmark.py                       # 10 万次基准 → data/benchmark_100k.json
```
