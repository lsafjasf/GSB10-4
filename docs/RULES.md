# 拆分规则说明

## 1. 归档格式

归档是多封邮件的字节拼接。每封邮件由一行**分隔标记**（marker，默认
`----MAIL-SEPARATOR----`）引出：

```
<marker>
<头部行...>
<空行>
<正文行...>
<空行>            <- 分隔符的一部分（定界空行），不属于上一封正文
<marker>
...
```

- 首封邮件前的 marker 可省略（归档开头即视为一封邮件的开始）。
- 正文中允许出现与 marker **逐字节相同**的行，拆分器必须能区分。

## 2. 分隔行判定依据

一行被判定为**真分隔符**，当且仅当同时满足：

| # | 条件 | 作用 |
|---|------|------|
| C1 | 行内容与 `marker` 逐字节相等（去掉行尾 `\n`/`\r\n` 后比较，不允许尾随空白） | 基本匹配 |
| C2 | 前一行是空行，或该行是归档第一行（`require_blank_before`，默认开） | 正文段落中间的同名行被排除 |
| C3 | 紧随其后的行构成一个**合法的 RFC 5322 头部块**：至少 `min_headers`（默认 2）个连续合法头部行，且头部块以空行结束（EOF 除外） | 正文中"marker + 普通文字"被排除 |
| C4 | （可选）头部块中必须出现 `required_headers` 指定的字段名（如 `From`、`Date`） | 正文中"marker + 少量形似头部的行"被排除 |

合法头部行 = 匹配 RFC 5322 `field-name:`
（`[\x21-\x39\x3b-\x7e]+:`，即可打印 ASCII 除冒号），或以空格/制表符开头的
折叠续行（续行不得出现在第一个头部之前）。

**关键细节**：头部块必须被空行**终止**。`marker` 后若出现
`X: y` 紧接普通文字（无空行），不视为头部块——真实邮件头部与正文之间
必有空行，而正文里随手写的"形似头部"通常没有。这条把误判率再压低一档。

## 3. 误判防护手段（分层）

1. **上下文双重校验**（默认）：C2 + C3 组合。正文里的 marker 行要造成误判，
   必须同时满足"前面恰好是空行"且"后面恰好是 ≥2 个以空行终止的合法头部行"
   ——自然文本几乎不可能偶然满足。
2. **必需字段白名单**：`required_headers=(b"from", b"date")` 时，正文里伪造
   出 `From:`+`Date:` 的概率进一步降低。适合已知归档必有这些字段的场景。
3. **转义模式**（`escape_prefix`，mbox 风格）：写出方把正文中等于 marker 的
   行写成 `<prefix><marker>`，拆分方无条件还原。此时 marker 行**无歧义**，
   上下文校验退化为纯防御。可控写出端时推荐启用。
4. **失败安全**：所有存疑情况一律**不拆**（保守方向），宁可漏拆不可错拆；
   漏拆会在消息数/诊断中体现，错拆则静默丢数据。

### 已知权衡（文档化的弱配置）

- `min_headers=1`：正文中"marker + 一行 `X: y` + 空行"会被误拆（测试
  `test_min_headers_one_accepts_headerlike_body` 演示了这一点）。默认 2。
- `allow_empty_headers=True`：允许"marker + 空行"引出无头部邮件。此时正文中
  "marker 行 + 空行"与分隔符**不可区分**，属于格式本身的歧义，只在归档
  确实含无头部邮件时开启。
- 定界空行归属：marker 前的空行属于分隔符。正文本身以空行结尾时，写出方
  需多写一个空行（拆分方只吃掉一个），保证往返一致。

## 4. 头部折叠还原（RFC 5322 §2.2.3）

- 以空格/制表符开头的行是上一头部的续行；展开 = **只删 CRLF，保留 WSP**，
  逐字节拼接，长行折行不丢任何内容（测试断言展开后长度逐字节相等）。
- 冒号后的可选空白按惯例去除（不属于字段值语义）。
- 续行出现在任何头部之前 → 诊断 `orphan-continuation`，不静默丢弃。

## 5. 编码与字符集：只报告，不猜

对每封邮件按声明做**严格校验**，失败一律写入 `diagnostics`，原始字节
原样保留，绝不替换成 `` 糊过去：

| 诊断 | 触发条件 |
|------|----------|
| `charset-missing` | 无 Content-Type 或未声明 charset |
| `unknown-charset` | 声明的 charset 在编解码器注册表中不存在 |
| `charset-decode-error` | 正文（传输解码后）按声明 charset 严格解码失败，如声明 utf-8 实为 latin-1、声明 us-ascii 含高位字节 |
| `cte-7bit-violation` | 声明 7bit 但正文含 >0x7F 字节 |
| `cte-decode-error` | base64 正文非法 |
| `unknown-content-transfer-encoding` | 未识别的传输编码 |

校验顺序：先按 Content-Transfer-Encoding 解码（base64/quoted-printable），
再按 charset 严格 `decode(errors="strict")` 试解码。

## 6. 其他诊断

`empty-message`、`no-headers`（缺头部）、`missing-blank-line`（头部后无空行）、
`malformed-header-line`、`orphan-continuation`。诊断只报告不修复。

## 7. 流式与内存

拆分器是单遍迭代器：行级读取 + 有限前瞻（仅前瞻到头部块结束即回放），
任意时刻内存中最多驻留**一封**邮件。峰值内存 = O(最大单封大小)，
与邮件数量无关（见 README 基准数据：消息数 8 倍增长，堆峰值恒定）。
