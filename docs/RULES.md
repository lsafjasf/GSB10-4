# 缓存键头部规范化规则（HK1 / v1）

设计铁律：**宁可把语义相同的请求拆成两个键（多占缓存），绝不把语义不同的请求
合并成一个键（错误命中）**。所有归一化规则要么有 RFC 明确背书，要么不做。

## 1. 哪些头部参与

- 调用方必须显式声明 `vary` 头部名单（对应 HTTP `Vary` 语义），**只有名单内的
  头部参与键**；名单外的头部（如 `Cookie`、`User-Agent`）一律忽略。
- `vary` 名单本身（小写排序后）连同每个头部的**策略指纹**一起进入键的前导，
  因此不同 vary 配置、不同策略配置产生的键绝不相同。
- 头部缺失与"值为空"是两种不同状态，编码不同，绝不合并。

## 2. 排序规则

| 对象 | 规则 |
|---|---|
| vary 头名 | 小写后按字典序排序（与声明顺序、大小写无关） |
| 请求中头行出现顺序 | 不参与键（按名归桶） |
| 同名重复头行 | 按 RFC 7230 §3.2.2 等价于逗号拼接后解析 |
| list 元素 | 默认**保序**（顺序常携带偏好语义）；仅当策略声明 `sort_elements` 才排序 |
| 参数（`;k=v`） | 仅当策略声明 `sort_params` 才按 (名, 值) 排序 |
| 重复元素/重复参数 | **不去重**，出现次数是信息 |

## 3. 归一化规则

### 3.1 对所有头部（安全基线，RFC 7230 背书）
- 头名：必须是合法 token（否则抛 `InvalidHeaderName`），转小写。
- obs-fold（`CRLF`+`SP/HTAB`）展开为一个 `SP`（RFC 7230 §3.2.4 明确规定其
  语义等价于 SP）。
- 其余控制字符（含裸 CR/LF、NUL、DEL）**拒绝**（抛 `InvalidHeaderValue`），
  不做"静默清洗"——清洗可能把两个不同值洗成同一个。
- 去除首尾 OWS（`SP`/`HTAB`）。RFC 7230 §3.2.4 规定首尾 OWS 在解析前即被
  移除，不属于字段值语义。

### 3.2 exact 模式（默认，未注册策略的头部一律走这里）
- 除 3.1 外**逐字节保留**：大小写、内部空白、顺序全部进键。
- 这是保守默认：不知道语义就不合并。`Authorization` 等头部因此天然安全。

### 3.3 list 模式（逗号列表语法，引号/反斜杠转义感知）
- 引号串外的 OWS 游程折叠为单个 `SP`（引号串内逐字节保留）。
- 按顶层逗号切元素；空元素丢弃（RFC 7230 §7：空元素无语义，接收方必须忽略）。
- 元素内按顶层分号切参数；参数名按策略可小写；参数值**永不折叠大小写**。
- 元素主 token 按策略可小写（仅引号串外）。

### 3.4 single 模式
- 同 list，但逗号视为普通字符（用于 `Content-Type` 这类单值带参头部）。

### 3.5 默认策略表（仅对规范明确声明"不敏感/无关"的语法做归一化）

| 头部 | 模式 | token 小写 | 参数名小写 | 参数排序 | 元素排序 |
|---|---|---|---|---|---|
| `accept` | list | ✓ | ✓ | ✓ | ✗（顺序=偏好） |
| `accept-encoding` | list | ✓ | ✓ | ✓ | ✗（顺序=偏好） |
| `accept-language` | list | ✓ | ✓ | ✓ | ✗（顺序=偏好） |
| `content-type` | single | ✓ | ✓ | ✓ | — |
| 其余一切 | exact | — | — | — | — |

依据：RFC 9110 §12.5（content negotiation 的 token/range 大小写不敏感）、
§8.3.1（media type 不敏感）、§8.4（参数名不敏感、参数值可能敏感）。

### 3.6 永不做的归一化（防合并红线）
- 参数值大小写不折叠（`charset=UTF-8` ≠ `charset=utf-8` 进不同键）。
- 引号串内容逐字节保留（含空白、大小写、逗号）。
- q 值等参数**不做数值归一**（`q=1` ≠ `q=01` ≠ `q=1.0`，字面量不同即不同键）。
- 不去重、不截断、不清洗控制字符。

## 4. 序列化与注入安全

规范化结果序列化为字节串（`canonical()`）：

```
HK1\n
<len>:<头名>\x00<策略指纹>  ...（按头名排序）
\n
每头一条记录： 0\x00            = 缺失
              1\x00<len>:<值>  = 存在（空值 = 1\x000:，与缺失可区分）
```

- 一切字段**长度前缀**（`<len>:`），可唯一解析；测试中用独立解码器对 3000
  组随机输入做了"编码→解码==恒等"的往返验证（`tests/run_tests.py`）。
- 因此值里出现 `:`、数字、换行编码等都不可能伪造成记录边界——朴素拼接的
  注入攻击（`X-A:"1,2"` vs `X-A:"1", X-B:"2"`）在本方案下天然免疫
  （见 pairs.json 反例）。

## 5. 键格式、长度上界与碰撞处理

```
规范化字节串长度 ≤ 256  →  可读键  "v1:" + 百分号编码（可逆、无碰撞）
否则                    →  哈希键  "h1:<原长>:<sha256-hex>"
```

- **长度硬上界 771 字符**（`MAX_KEY_LEN`）：可读键最坏每字节 `%XX`，
  3 + 3×256 = 771；哈希键 ≤ 3+5+1+64 = 73，恒更小。
- **绝不截断**：超长输入走哈希档；参与键的头部块超过 64 KiB 直接抛
  `HeaderBlockTooLarge`，拒绝构造。
- 碰撞分析：
  - `v1` 档：编码可逆，碰撞当且仅当规范化字节串相同（构造性无碰撞）。
  - `h1` 档：碰撞下界 = SHA-256 抗碰撞性（2^128 生日界），并携带原始长度
    标签，长度不同的输入即使摘要相同键也不同。
  - 两档前缀不同（`v1:`/`h1:`），跨档不可能碰撞。
- 键为单行纯 ASCII，不含空白与控制字符，可直接用作任意存储的键。

## 6. 版本化

`HK1`（序列化版本）与 `v1`/`h1`（键版本）均进入键本身。任何规则变更必须
升级版本号，新旧键自然隔离，不会发生跨版本误命中。
